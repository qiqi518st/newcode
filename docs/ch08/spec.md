# NewCode ch08 — 上下文管理 需求规格 (spec.md)

## 背景

NewCode 自 ch04 起拥有 Agent Loop，能多轮连环调用工具；ch06 给工具调用装上五层权限；ch07 接上 MCP 让工具生态可插拔。但用得越多，对话历史越长：每一轮的工具结果（文件内容、命令输出、MCP 返回）原样堆进历史，Token 消耗直线飙升。当前唯一的「窗口管理」是 ch02 遗留的滑动窗口 `_trim`——它按**消息条数**裁剪、只在纯文本 assistant 回复后触发、工具回合完全不裁剪，且整对丢弃会破坏 Anthropic 强制的 tool_use/tool_result 配对。长工具结果无限堆积，最终撞穿上下文窗口，Agent 瘫掉。

在实际编码场景下，工具结果（ReadFile、Bash、Grep、MCP 返回）是 Token 占用的绝对大头，实测一般占整轮请求的 80%~90%。把一份十几万字符的源文件原样反复塞进每一轮请求，是上下文耗尽的主要诱因。不同 provider 的上下文窗口差异很大（Anthropic 默认 200K、OpenAI 默认 128K），固定阈值无法跨 provider 通用。ch06 权限引擎、ch07 MCP 客户端只解决「单轮如何安全执行」，长时间连续工作的「对话本身越来越长」问题还没人管。ch08 要补的就是这一块：让 Agent 能在一个进程内连续工作数小时，而不因对话历史撑爆 context 被中断。

设计思路是**两层防御**。第一层在工具结果产生的瞬间就动手：把超大的单条结果落盘，对话里只留头部预览和文件路径，从源头压住膨胀曲线；它是确定性纯函数式字符串替换，**不调用 LLM**。第二层是兜底：当估算 Token 接近模型上下文窗口时，发起一次 LLM 全量摘要，把多轮历史浓缩成一份结构化纪要，再追加一段「恢复」内容把摘要无法精确还原的关键事实（最近读过的文件原文、当前可用工具、边界提示）补回来。第一层是预防，第二层是急救，两层互相独立但配合作战。两层都在 Agent Loop 每轮发起请求前自动执行，压缩结果赋值回外层对话历史；用户也可随时 `/compact` 手动触发。当自动阈值因估算偏差或异常巨大的单轮结果而没能挡住、请求被 API 以 `prompt_too_long` 拒绝时，AgentLoop 兜底触发一次紧急压缩。

> **字节口径说明**：本文档中第一层的 50000 / 200000 阈值与预览体头部的 2048 阈值均指 `len(content.encode("utf-8"))` 返回的**字节数**（Python 字符串底层是 Unicode 码点，对超大文本判断时统一编码到 UTF-8 计量；一个中文 3 字节），不是 `len(str)` 的字符数。下文第一层出现的「字符」统一按 UTF-8 字节计算，便于实现层用 `len(s.encode("utf-8"))` 直接判断。第二层的 Token 阈值另用估算口径（见 F13/F14）。

## 目标

- **G1 长时连续工作**：在单进程会话内，能够连续工作数小时不因上下文超长而被 provider 拒绝。
- **G2 缓存友好**：同一个工具结果在被替换后，每一轮回放的字符串必须逐字节一致；替换决策一经作出会话内永不翻转，保护 PromptCache 命中率。
- **G3 用户原话不丢**：用户消息原文不丢，模型可通过摘要 + 恢复段还原「用户到底要我做什么」。
- **G4 落盘可重读**：被替换或被摘要掉的工具结果在物理上仍可访问，模型可用文件读取工具显式重读。
- **G5 自动/手动共用核心**：自动压缩与手动压缩共用核心摘要路径，但触发条件、阈值、熔断行为有所区分。
- **G6 撞墙兜底**：对 provider 撞墙（`prompt_too_long`）有紧急压缩 + 重试机制，不让一次撞墙就丢掉用户的最新输入。
- **G7 跨 provider 通用**：上下文窗口大小通过模型能力解析驱动，未识别时按 provider 协议给出合理默认值。
- **G8 模块隔离**：上下文管理引入的所有新代码集中在专属模块内，对 Agent 主循环只暴露窄接口；功能可被关闭或绕过测试。
- **G9 Skill 骨架就位**：建立 Skill 最小骨架类与注册容器，使压缩后恢复的 Skill 注入有代码挂载点；Skill 内容加载留待后续章节。

## 功能需求

### 第 1 层：单条与单轮工具结果预防性压缩

#### F1: 单条结果存盘（字节阈值）

当某一次工具调用返回的内容字节数超过**单条阈值（50000 字节）**时，系统必须把完整结果落盘，对话里只保留该工具结果的「预览替换体」。估算口径为 `len(content.encode("utf-8"))`。

#### F2: 单轮聚合存盘

每一组工具调用回合对应一条 RoleTool 消息（NewCode 把同一回合的工具结果挂在该消息的 `tool_results` 列表里）。系统先剔除已被 F1 单条阈值命中而决策为替换的项，再对该消息上剩余项的 `content` 字节做聚合判断：若聚合字节数超过**单轮聚合阈值（200000 字节）**，按字节从大到小依次把工具结果落盘，直到剩余项的聚合字节数回落到 ≤ 200000。F1 已替换的项不再参与 F2 聚合判断。

#### F2a: 三步原子（落盘 → 改写 content → 写账本）

F1 与 F2 共用一次扫描：实现层对每条 RoleTool 消息的 `tool_results` 列表建立候选列表后按字节倒序处理；先把超过单条阈值的项落盘，再按聚合预算继续落盘下一项，直到剩余聚合 ≤ 单轮聚合阈值。**落盘 → 改写 content → 写入账本**三个动作必须按固定顺序串行执行，**任一步失败则三件都不发生**（保持原文 + 不写账本），保证 content 与账本始终一致。

#### F3: 幂等落盘（文件名 = tool_use_id）

落盘文件名必须等于该工具调用的 `tool_use_id`（Anthropic）或 `tool_call_id`（OpenAI）；同一个 id 已落盘过就跳过，不重复写。`tool_use_id`/`tool_call_id` 为空（边界/mock 场景）时用兜底命名（自增序号等），不抛。

#### F4: 预览替换体结构

替换体在对话中必须以**稳定的字符串**形式呈现，必须包含四项信息：

1. **原始字节数元信息**；
2. **头部预览**：取该工具结果的前 20 行或前 2048 字节中的较短者（先按行截到 20 行，再按字节截到 2048，二者择短，保证预览长度可控）；
3. **落盘文件路径**；
4. **重读提示**：明确告知模型如需完整内容请用文件读取工具读取该路径。

预览字符串一经生成即缓存复用，后续每一轮逐字节一致（见 F5d）。

#### F5: 决策冻结（ContentReplacementState 四子项）

系统维护一个会话级的 `ContentReplacementState`（已见集合 `seen_ids` + id→预览字符串映射 `replacements`），记录每个工具结果的替换决策。账本更新满足四条子项：

- **(a) 只在决策完成后写入**：账本只在第 1 层完成对该 id 的决策动作后写入；
- **(b) 落盘失败不进账本**：落盘失败的 id 既不计入 `seen_ids` 也不计入 `replacements`，下次组装请求时重新评估；
- **(c) 同轮最多评估一次**：同一个 id 在同一轮内最多被评估一次（已决策的项跳过后续聚合判定，避免重复算入预算）；
- **(d) 永不翻转 + 预览字符串冻结**：一旦写入 `seen_ids`，无论是「保留原文」还是「替换」，本会话内不再翻转；被决定为「替换」的 id 之后每一轮都用**同一份预览字符串**（同一个 str 对象，不允许重新构造）替换。

#### F6: 确定性纯函数式替换

第 1 层压缩在 Agent 每次组装 LLM 请求体之前执行，是**确定性的、纯函数式的字符串替换，不调用 LLM**。它必须在毫秒级完成（N1）。

### 第 2 层：LLM 全量摘要

#### F7: 自动触发阈值（绝对值）

当估算 Token 达到自动触发阈值（`context_window − 摘要预留输出 20000 − 自动安全余量 13000`，即 `context_window − 33000`）时，系统必须在下一次 LLM 请求发出之前完成一次摘要。其中 20000 是给摘要本身的预留输出空间，13000 是估算误差与单轮波动的安全余量，防止「看上去差一点点」实际已经撞墙。总 Token 估算 ≥ 触发阈值即触发。

**context_window 下界检查**：若 `context_window ≤ 33000`（摘要预留 + 自动安全余量之和），则触发阈值 `窗口−33000` 为非正数、判断永远成立，会导致每轮都触发摘要死循环。此时自动路径必须跳过第二层摘要（仅跑第一层），并输出一条 `logging.warning` 说明窗口过小。

#### F8: 摘要请求不传工具

摘要请求体**不传任何工具定义**。摘要本身不允许调用工具。

#### F9: 草稿 + 正文两阶段

摘要分两阶段：先让模型在 `<analysis>` 标签内写出分析草稿，再在 `<summary>` 标签内写出正式摘要。**草稿丢弃，只保留正式摘要**。

#### F10: 九段结构化摘要

正式摘要必须遵循固定的 9 部分结构：

1. 主要请求和意图；
2. 关键技术概念；
3. 文件和代码段；
4. 错误和修复；
5. 问题解决过程；
6. **所有用户消息原文优先逐条保留**；
7. 待办任务；
8. 当前工作（最详细的一段，覆盖正在做什么、停在哪一步）；
9. 可能的下一步。

用户原始消息尽量原文保留、不被摘要改写——通过第 6 部分原文收录实现；这些用户原话**不作为独立消息保留**，只折叠进摘要第 6 部分。

#### F11: 近期原文保留（双下界，择宽）

摘要完成后，需要从原对话尾部保留一段「近期原文」接在摘要之后（在恢复段之后，见 F15）。保留策略：从尾部开始倒序累加，直到**累计估算 Token ≥ 10000 且 累计消息条数 ≥ 5**（两个下界都满足后才停手）。「择宽」在本文档中的含义是「同时满足两个下界、覆盖范围更大」，不是「任一满足即停」（任一满足即停反而是择窄，会让保留量比设计小）。

#### F12: 近期原文不拆 tool_use/tool_result 对

保留近期原文时不允许把一对 `tool_use` 和 `tool_result` 切开。如果按 Token/消息数算出来的截断点正好夹在工具调用和工具结果中间，必须把截断点**向前推到工具调用之前**。

#### F13: Token 估算（锚定真实 usage + 增量）

系统必须能在不调用精确 tokenizer 的前提下估算「如果现在发请求要消耗多少 Token」。估算**锚定上一次 provider 返回的真实 usage**（input + cache_read + cache_creation + output 之和），并对其后新增的消息内容按 `字符数 / 3.5`（常量 `ESTIMATE_CHARS_PER_TOKEN = 3.5`）做增量估算。估算偏保守（宁可高估）。

#### F14: 锚点更新（替换不累加）

每次 LLM 请求结束后，系统必须从流尾事件中捕获 usage 数据并**替换**（不是累加）锚点。估算函数在两次真实请求之间按 `字符数 / 3.5` 做增量估算。

### 压缩后恢复（三段）

#### F15: 恢复段位置与三块内容

第 2 层摘要完成后，系统必须在**摘要之后、近期原文之前**追加一段恢复内容，分三块：最近读过的文件快照、当前可用工具列表、边界提示消息。

**摘要 + 恢复段合并为单条 user 消息**：为保证 provider（尤其 Anthropic，强制 user/assistant 交替）不因连续 user 消息拒绝请求，摘要正文与恢复段三块必须拼进**同一条 `role="user"` 消息的 content**（摘要写在前、恢复三段紧随其后），不得各自成独立 user 消息。拼接后若近期原文的首条消息也是 `role="user"`，则在恢复段与近期原文之间插入一条空的 `assistant` 消息作衔接占位，保住交替约束。

#### F16: 最近文件快照（5 个 × 5000 token）

最近读过的文件快照最多 5 个，按「最后一次成功读取的时间戳」倒序排列。每个文件内容上限 5000 token；超过时保留头部 5000 token 对应的字符片段（按 `int(5000 * ESTIMATE_CHARS_PER_TOKEN)` 估算字符数），截掉尾部多余内容，并在尾部追加一行 `(content truncated)` 标注。每个文件展示路径、读取时间戳、内容片段。

#### F17: 工具列表一致性（同一份引用）

当前可用工具列表必须与下一次 LLM 请求实际传给 provider 的 tools 参数**严格一致**——同一份工具集合在恢复段声明和在请求 tools 字段里出现的工具数量、工具名、参数 schema 都必须对得上。为保证一致性，恢复段所读取的工具定义与当次 stream 请求传给 provider 的 `tools` 必须来自主循环本轮迭代开头按当前权限模式（普通/规划）一次性算出的**同一份列表引用**（`id(defs)` 相同），不允许在恢复段构造与 stream 调用之间独立重算或选择不同子集。本章承诺的工具一致性以 `Agent.run` 的单次迭代为粒度；跨迭代或跨 run 调用之间允许工具集变化。

#### F18: 边界提示固定文案

边界提示消息是固定文案，明确告诉模型：需要文件原文、错误原文、用户原话时请用文件读取工具重读，不要靠摘要猜测。

#### F19: 文件追踪（纯净字节记录）

文件追踪发生在 Agent 主循环里：每当文件读取工具成功返回后，系统必须用**纯净字节**（不带行号前缀的原始内容）重新记录一次到文件追踪状态，作为恢复段的数据源。

#### F19a: 文件追踪与回填同 task 顺序执行

文件追踪的写入必须与工具结果回填到 Conversation 在**同一个 asyncio task 内顺序发生**（即在 `execute_batched` 完成工具调用后、`add_tool_results` 之前同步 `await` 完成），保证下一次 `manage_context` 能观察到本轮 ReadFile 的记录。

#### F20: 文件追踪并发安全

文件追踪状态在被工具回调和主循环并发访问的场景下必须是线程安全/异步安全的（用 `asyncio.Lock` 或 `threading.RLock` 保护）。

### 手动入口

#### F21: 斜杠命令统一注册表

TUI 输入框收到以斜杠开头的输入时，必须走命令路径，不发送给 LLM。本章把已有的 `/exit`、`/plan`、`/do` 命令一并迁移到统一注册表 `BUILTIN_COMMANDS` 下（行为不变），同时新增 `/compact` 内置命令；未注册命令走未知命令兜底，给出可用命令提示，不发送给 LLM。命令路径不写入 conversation，命令执行结果只通过系统消息在 TUI 视图层展示。

#### F22: /compact 无条件触发摘要

`/compact` 跳过第 1 层、跳过阈值检查、跳过自动触发闸，无条件触发一次 LLM 摘要。「跳过第 1 层」仅指本次手动触发动作本身不调用第 1 层；摘要完成后 Conversation 被替换为新消息列表，Agent 下一次发请求前的常规第 1 层（自动路径）继续生效。

#### F23: 手动余量仅用于摘要请求自检

手动 `/compact` 不做阈值判断，无条件触发摘要。**3000 这个安全余量仅用于判断摘要请求自身的 messages**（即摘要 prompt 序列化后的输入）估算 Token 是否已经超过 `context_window − 20000 − 3000`；如果超过则直接进入 F27 的丢消息组重试，不让请求白白撞墙。它**不是**触发阈值。

#### F24: 手动压缩结果提示

手动压缩完成后，TUI 必须显示一条系统消息，告诉用户压缩前后估算 Token 数的变化（「压缩前 N → 压缩后 M（节省 N−M）」）。

#### F24a: 自动压缩 UX

自动压缩触发时 TUI 必须立即显示一条状态提示（如「正在压缩上下文...」），完成后追加「已压缩，token 从 X 降至 Y」，避免用户以为程序卡死。

#### F24b: 紧急压缩 UX

紧急压缩触发时 TUI 同样显示状态提示，前缀为「上下文撞墙，自动压缩中...」；完成后追加压缩结果或错误信息。

### 异常路径

#### F25: ForceCompact 紧急压缩

Agent 主循环在调用 provider 时如果收到 `prompt_too_long` 类错误，必须立即触发一次紧急压缩，然后用压缩后的新消息列表把刚才那个请求重试一次。紧急压缩与手动 `/compact` 共用同一条核心路径，但紧急压缩在调用摘要前**必须先强制跑一次第 1 层**（`offload_and_snip`）把单条 50K+ 工具结果挪到磁盘，避免摘要请求自己也立刻撞 PTL。紧急压缩内部发起的摘要请求若自身撞 `prompt_too_long`，仍走 F27 的丢消息组重试策略；F27 是所有摘要请求（自动 / 手动 / 紧急）共用的底层处理。

#### F25a: 紧急压缩后重估 + 不可恢复上抛

紧急压缩成功后，系统必须使用新的消息序列与**重置后的锚点**（`usage_anchor` 临时清零）重新估算 Token；只有在估算低于 `context_window − 手动安全余量 3000` 时才进行重试，否则视为不可恢复错误上抛，不再做第二次紧急压缩。

#### F26: 紧急压缩后重试原请求一次

紧急压缩后的重试只重试一次。重试仍失败的话，按正常错误流程上抛，不再二次重试。Agent 在主循环内用一个 `emergency_retried` 局部标记保证一次迭代内只重试一次。

#### F27: 摘要请求自身 PTL 的统一处理（三路径共用）

如果摘要请求自身也撞了 `prompt_too_long`，系统必须把当前对话按「用户提交 → 一组 assistant/tool 往返」分组，丢弃最旧的若干组，用剩余消息重新发起摘要请求。这一过程最多 **3 次直接重试**（即除初始请求外的 3 次重试，每次丢最旧 1 组）；3 次仍失败后，每次再丢 `math.ceil(剩余组数 × 0.2)`（至少 1 组）继续，直至摘要请求能塞下，或者全部消息都被丢光。若所有消息组都被丢光摘要请求仍然失败，按一次摘要失败上抛错误。系统**不会**尝试发送 messages 为空的摘要请求。

#### F28: 单次压缩行动重试上限（熔断模型）

**每一次压缩行动**——无论是自动阈值触发、手动 `/compact`、还是紧急 ForceCompact——都独立拥有自己的「最多重试 3 次」上限。重试发生在**同一次压缩行动内部**（摘要请求失败 → 走 F27 丢消息组重试，最多 3 次直接重试 + 其后按 20% 递增）。**不存在跨种类、跨行动的计数累加**：上一行动的失败不计入下一行动；上一行动的成功也不重置别的行动。

「熔断」的含义是**这一次压缩行动的 3 次重试都没成**，那一次行动就此放弃。三种触发路径的熔断收尾统一为**弹同一套选择菜单**交用户处置，差异只在收尾补充：

- **自动路径**：本次自动压缩放弃、本轮自动触发停止、stderr 报错、弹选择菜单（重试 / 分组丢弃重试（标明丢量）/ 放弃 / 退出 / 其他说明）。
- **手动路径**：本次手动压缩放弃、TUI 显示失败原因、弹同一选择菜单。用户可重选再起一次新的手动压缩行动（又有自己的 3 次）。
- **紧急路径**：本次紧急压缩放弃、stderr 报错、弹同一选择菜单。原请求不再重试。

**自动路径连续失败闸（防菜单轰炸）**：在上述「单次行动独立 3 次」之外，自动路径额外维护一个「连续失败轮数」计数器：**连续 3 轮**自动压缩行动都失败（每行动内部已重试 3 次仍未成）后，**停止自动触发**——后续轮次自动路径不再触发摘要、也不再弹菜单（静默跳过 L2，仅跑 L1），直到用户手动 `/compact` **成功一次**即解除闸、恢复自动压缩。该闸**只作用于自动路径**，手动 /compact 与紧急压缩不受限（不跨种类）；它与「无跨行动计数」并存——闸记录的是「连续几轮自动行动失败」，不是会话级失败总额，不改变单次行动内部的 3 次重试。

分组丢弃重试流程（用户在菜单选中即启动，选中即视为确认）：按 user 消息分界把历史分成若干组 → 每次丢弃最旧的 2 组 → 用剩余消息重试摘要 → 最多重试 3 次 → 3 次仍不行则每次丢弃 20% 的组再试 → 直到成功或无组可丢。组以「一条 user + 其后到下一条 user 之前的所有 assistant / tool_use / tool_result」为单位，整组丢弃天然保住 tool_use/tool_result 配对。

### Context Window 解析

#### F29: getContextWindowForModel 四级优先

提供按当前模型解析上下文窗口上限的能力，严格按以下优先级**依序**判定（前一级命中即返回，不再往下）：

1. **环境变量硬覆盖**：`CLAUDE_CODE_MAX_CONTEXT_TOKENS` 已设置 → 直接取该值（如手动设为 1,000,000）。
2. **模型名后缀**：模型名带 `[1m]` 后缀（如 `claude-sonnet-4-20250514[1m]`）→ 取 1,000,000。
3. **模型能力表**：能力表中有该模型且其最大输入 Token ≥ 100K → 取能力表标注的上限。
4. **协议默认**：以上都不满足 → 按 provider 协议给默认值（anthropic 200000、openai 128000）。

能力表维护一份**已知大上下文模型**的最大输入 Token（仅收录 ≥100K 的模型，使第 3 级有意义；<100K 的模型不进表，落入第 4 级协议默认）。解析永不抛：查表 miss、模型名异常等情形落入第 4 级协议默认。

#### F30: 能力表探测脚本（独立交付）

ch08 额外交付一个**独立探测脚本**（如 `scripts/probe_context_window.py`），用于在能力表没有某模型数据时程序化估算其上下文长度：脚本对目标模型发逐步增长的 prompt 直到 provider 返回 `prompt_too_long`，二分逼近边界。该脚本：

- **不在 Agent 主流程内**、**不被 F29 引用**、不引入运行时网络依赖；
- 依赖有效 API key 与网络，由开发者手动运行；
- 产出的数字由开发者**手工**填进能力表源码并提交，不自动回填；
- 探测结果是经验下界（受系统提示、工具定义、provider 预留输出影响），不是官方上限，填入时在能力表旁注明来源与探测时间。

### Skill 骨架

#### F31: Skill 最小骨架（为恢复段注入留挂载点）

建立 Skill 的最小骨架，为 F15 之后的 Skill 注入（当前恢复段只含文件快照 + 工具列表 + 边界提示三块，Skill 注入为预留挂载点）提供代码挂载点，**不实现 Skill 内容加载**：

- **Skill 数据类**：表示一个 Skill 的最小结构（名字、描述、内容占位等，具体字段在 plan 中定）。
- **SkillRegistry**：注册与查询 Skill 的容器（注册、按名查询、列举）。
- **注入挂载**：恢复段链路预留 Skill 注入分支——查 registry，有 Skill 则按 25,000 tokens 预算注入稳定提示，空则跳过。
- **内容加载留空**：Skill 定义从何处读取、如何填充内容，以 TODO/占位注释标记，留待后续章节。ch08 不补全此部分。

### 配置与生命周期

#### F32: 阈值全部硬编码、不暴露配置项

所有阈值与常量在系统内部硬编码，**不暴露为任何配置项**（不进 YAML、不进 env，env 只保留 F29 第 1 级的 `CLAUDE_CODE_MAX_CONTEXT_TOKENS`）：单条工具结果阈值 50000 字节、单轮聚合阈值 200000 字节、摘要输出预留 20000 token、自动安全余量 13000 token、手动安全余量 3000 token、近期原文 token 下界 10000、近期原文条数下界 5、最大近期文件数 5、单文件快照 token 上限 5000、单次压缩行动重试上限 3、熔断菜单分组丢弃每次组数 2、摘要 PTL 直接重试上限 3、PTL 比例丢弃步长 0.2、自动路径连续失败闸阈值 3、字符→token 估算比 3.5、预览体头部字节上限 2048、预览体头部行数上限 20、context_window 下界 33000、`[1m]` 后缀窗口 1000000、协议默认窗口（anthropic 200000 / openai 128000）、Skill 恢复预算 25000。这些常量的调整属于代码变更，不属于配置变更。

#### F33: 会话 id 与落盘路径

会话 id 在进程启动时生成一次，格式为 `<unix_ts>-<short_random>`。会话 id 在进程内全局唯一，不持久化，进程退出不自动清理本会话目录。所有落盘的工具结果写到 `.newcode/sessions/<session_id>/tool-results/<tool_use_id>` 路径下。该目录必须按需创建，已存在时不报错。

#### F34: 手动 / 主循环互斥

手动 `/compact` 与 Agent 主循环不允许并发执行。要么 TUI 在主循环空闲（即一次 `run` 调用结束）时才触发；要么 Agent 在 `run` 期间持一把会话级锁（`asyncio.Lock`），`run_force_compact` 必须等待该锁。

## 非功能需求

- **N1（性能）**：第 1 层压缩是纯字符串处理，在每轮组装请求时必须能在毫秒级完成；落盘 I/O 可同步（`pathlib.Path.write_bytes`）亦可走 `asyncio.to_thread`，但不能阻塞 asyncio event loop 超过 100ms 的量级。
- **N2（并发安全）**：替换决策账本（已见集合 + id→预览字符串映射）、文件追踪状态两类状态在 asyncio task / 后台线程混用场景下都必须并发安全；任意一种状态在 TUI 命令路径、Agent 主循环、紧急压缩路径同时访问时不允许出现读写竞态。账本的「读账本 → 决策 → 写账本」必须在同一把锁的同一临界区内原子完成（`asyncio.Lock` 或 `threading.RLock`），不允许出现「某 id 已 Seen 但 replacement 还没写入」的中间态；也不允许出现某个 id 的替换字符串在同一轮请求里出现两个不同版本。
- **N3（配对完整性）**：tool_use 与 tool_result 必须成对存活或成对消失。第 1 层就地改写只动 tool_result 内容不动配对结构；第 2 层摘要与分组丢弃都以「一条 user + 其后到下一条 user 之前」为整组单位，不拆对。遗留 `_trim` 的整对丢弃须修正为不拆对、降级为条数兜底。
- **N4（幂等与不丢数据）**：第 1 层存盘文件名取 `tool_use_id`，文件已存在即跳过写入复用，同一结果多次判定幂等；磁盘写入失败降级为不替换该条 + stderr 告警，不致会话崩。任何丢数据动作（摘要替换、分组丢弃）执行前必有用户确认入口（F28 菜单选中 / 紧急路径在 F27 内部丢组属同一行动内部重试，无需额外确认）。
- **N5（熔断与兜底不卡死）**：每一次压缩行动有独立 3 次重试上限、用完即放弃并交用户菜单，不无限重试、不自行硬截断；紧急压缩有 `emergency_retried` 标记保证一次迭代内只重试一次。两条路径都不会让 Agent Loop 挂在压缩里出不来。
- **N6（跨协议一致）**：两层压缩与 Context Window 解析对 provider（Anthropic / OpenAI）中立；`tool_use_id`（Anthropic）与 `tool_call_id`（OpenAI）都作为第 1 层文件名来源；provider 适配层的错误识别（`prompt_too_long`）要覆盖两家。
- **N7（既有能力不退化）**：ch01–ch07 的会话、Loop、流式、缓存、规划、权限、MCP、并发、用户取消、保序回灌等行为不退化。`_trim` 改造不得破坏 ch02 既有测试的语义（条数裁剪兜底仍在，只是不再作为主裁剪）。
- **N8（向后兼容）**：未启用任何新字段的旧配置文件必须仍然可以正常加载；运行时即使从未触发压缩，也不影响 Agent 原有行为。
- **N9（可测性）**：核心逻辑（替换决策、Token 估算、消息分组与丢弃、近期原文边界推算、Context Window 四级解析）必须能脱离真实 provider 单元测试；测试 fixture 不依赖网络（pytest 用 monkeypatch 注入 fake provider）。
- **N10（可调试性）**：每次触发压缩都要输出可追踪的日志或事件（`logging.getLogger(__name__).info(...)`），至少包含触发原因（自动 / 手动 / 紧急）、压缩前估算 Token、压缩后估算 Token、被替换的工具结果数量。
- **N11（错误隔离）**：第 1 层落盘失败必须降级为不替换该条工具结果，不能因为磁盘问题让对话中断；第 2 层摘要失败必须按 F28 熔断模型（单次行动独立 3 次重试 + 自动路径连续失败闸）记录，不能因为单次摘要失败让 Agent 进程崩溃（所有外部异常在 compact 包入口处都被 `try/except Exception` 兜底）。
- **N12（代码规范）**：`ruff check` / `ruff format --check` / `mypy`（可选 strict 子集）/ `pytest` 全过；异步测试沿用 repo 现有 `@pytest.mark.anyio` 标记（非 `pytest-asyncio`）。
- **N13（落盘与凭据）**：不把凭据/敏感信息回显到落盘文件外的任何输出（落盘文件本身是工具结果，可能含敏感内容，但只写本地、不外发）；进程退出不自动清理本会话目录，便于调试回看。

## 不做的事

- **精确 tokenizer**——估算锚定 provider 返回的真实 usage，新增内容按字符数除以 3.5 估算。引入 `tiktoken` / `anthropic-tokenizer` 会增加依赖与计算开销，而锚定真实 usage 已经足够稳定。
- **压缩策略的机器学习优化**——阈值与触发规则为手工设定的固定策略，不学习、不自适应、不做线上 A/B、不做摘要质量评分回流。
- **Skill 内容加载**——F31 只建骨架与注入挂载点，不实现从文件/远端读取 Skill 定义并填充内容（留待后续章节）；ch08 恢复段实际只输出文件快照 + 工具列表 + 边界提示三块，Skill 注入分支为空实现。
- **能力表自动回填**——F30 探测脚本产出的数字由开发者手工填进能力表源码，不做运行时自动写回外部数据文件、不把能力表做成可读写数据资产。
- **跨会话持久化**——`ContentReplacementState`、最近文件追踪器、落盘文件索引均随会话存活、不跨会话恢复；落盘的大结果文件本身留在磁盘但下个会话不自动复用其索引。
- **多 provider 差异化压缩**——两层压缩逻辑对两家 provider 一致，不做 provider 专属优化。
- **压缩过程的完整审计日志**——只做 N10 的关键日志与 `/compact` 前后 Token 展示，不做完整审计链路。
- **自动压缩的细粒度回滚**——摘要替换一旦执行不回滚（除非用户手动重新发起）。
- **大结果文件的自动清理/GC**——落盘文件的生命周期管理留待后续；进程退出不清理本会话目录。
- **`prompt_too_long` 之外的请求级兜底**——鉴权、网络、限流等错误不触发 ForceCompact，走既有错误处理。
- **阈值开放为配置项**——除 F29 第 1 级 env 硬覆盖外，所有阈值硬编码，不进 YAML。
- **跨种类/跨行动的熔断计数累加**——每次压缩行动独立拥有自己的 3 次重试上限，不存在会话级累计失败计数器。
- **修改 ch01–ch07 既有功能的对外行为**——仅改造 `_trim` 内部使其不拆对、降级为兜底，不删条数裁剪能力本身；`/exit`、`/plan`、`/do` 迁移到 `BUILTIN_COMMANDS` 行为不变。
- **同进程多 Agent 实例并发**——当前进程内只有一个 Agent；多实例并发涉及状态隔离、目录隔离等额外问题，不在本章范围。

## 验收标准

- **AC1（单条预防）**：构造一次返回 60000 字节的工具调用 → 对话中该工具结果被替换为预览体，包含原始字节数、头部预览、落盘路径、重读提示四项；预览体头部内容长度同时不超过 20 行且不超过 2048 字节；`.newcode/sessions/<session_id>/tool-results/<tool_use_id>` 下能找到完整原文。F1/F4/F33
- **AC2（单轮聚合预防）**：构造一条 RoleTool 消息触发 3 条工具结果，每条 80000 字节（合计 240000，超 200000 阈值）→ 系统按字节大→小依次落盘，直到聚合回落到 200000 以下；被替换的工具结果数量等于「足以让聚合达标」的最小数量。F2/F2a
- **AC3（幂等落盘）**：对同一个 `tool_use_id` 触发两次第 1 层压缩 → 落盘文件只写一次（文件 `os.stat().st_mtime_ns` 不变），第二次跳过 I/O。F3
- **AC4（决策冻结）**：某个 `tool_use_id` 在第 N 轮被决定不替换 → 此后任意一轮组装请求时该工具结果都保持原文；某个 `tool_use_id` 在第 M 轮被决定替换 → 此后任意一轮组装请求时使用的预览字符串都与第 M 轮逐字节一致（`id(s)` 不要求相同，但 `s1 == s2`）。子断言：构造一个落盘失败场景，该 id 不进入 `seen_ids`，下一轮组装请求时仍可被重新评估并尝试落盘。F5
- **AC5（自动触发阈值）**：当估算 Token 跨过 `context_window − 33000` 边界 → 下一次 LLM 请求发出前自动执行一次摘要；估算 Token 未跨过该边界时不触发。F7/F13/F14
- **AC5a（下界 sanity check）**：设置 `CLAUDE_CODE_MAX_CONTEXT_TOKENS` 为 30000（< 33000）→ 自动路径跳过第二层摘要、仅跑第一层、输出一条 `logging.warning`，且不出现每轮反复触发摘要的行为。F7
- **AC6（摘要请求无工具）**：抓取摘要发往 provider 的请求体 → tools 字段为空或不存在。F8
- **AC7（摘要结构）**：摘要返回内容只保留 `<summary>` 部分，可解析出 9 个固定小节，且第 6 节中能找到本会话所有用户消息的原文。F9/F10
- **AC8（近期原文保留边界）**：摘要后对话中除摘要本身和恢复三段之外，保留的「近期原文」满足：累计估算 Token ≥ 10000 **且**条数 ≥ 5（两个下界都满足）；且最前面一条不是落单的 `tool_result`。F11/F12
- **AC8a（摘要+恢复合并单条 user + role 衔接）**：摘要后新消息列表首条是**单条 `role="user"`** 消息，其 content 内含 9 段摘要正文与恢复三段全部文字；新列表全程不存在连续两条 `role="user"` 消息（若近期原文首条为 user 则在中间有 `assistant` 衔接占位）。F10/F15
- **AC9（恢复三段-文件快照）**：在压缩前依次读过 7 个不同文件 → 恢复段只展示最后 5 个，按时间戳倒序；每个文件超过 5000 token 时只保留头部对应字符片段（截掉尾部多余内容），尾部出现 `(content truncated)` 标注。F16/F19/F20
- **AC10（恢复三段-工具一致）**：恢复段中列出的工具名集合 == 紧接其后的那次 LLM 请求 tools 参数中的工具名集合，逐项可对应。子断言：恢复段读取的工具定义列表与 Stream 请求的 `tools` 列表来自同一引用（`id(defs)` 相同），而非分别构造后内容相等。F17
- **AC11（恢复三段-边界提示）**：恢复段包含固定文案的边界提示消息，告知模型需要原文请重读，不要靠摘要猜测。F18
- **AC12（手动入口路由）**：在 TUI 输入 `/compact` → 不会触发任何 LLM 普通对话请求，只会触发一次摘要请求；输入 `/unknown` 之类未注册命令 → 给出友好提示（含可用命令），也不发给 LLM。F21
- **AC13（手动入口跳过阈值）**：在估算 Token 远低于自动阈值时输入 `/compact` → 仍然执行一次摘要，不被阈值检查拦截。F22/F23
- **AC14（手动入口跳过熔断）**：人为让上一次自动摘要的压缩行动 3 次重试都没成（本次行动熔断）→ 此时输入 `/compact` 仍然能正常起一次新的手动压缩行动（有自己的 3 次重试），不被上一行动的熔断拖累。F22/F28
- **AC15（手动入口提示）**：`/compact` 成功后 TUI 显示一条系统消息，包含压缩前和压缩后的估算 Token 数。F24
- **AC16（自动/紧急压缩 UX）**：自动压缩触发时 TUI 立即显示「正在压缩上下文...」，完成后追加「已压缩，token 从 X 降至 Y」；紧急压缩触发时显示「上下文撞墙，自动压缩中...」，完成后追加结果或错误。F24a/F24b
- **AC17（紧急压缩）**：mock provider 在第 K 次请求返回 `prompt_too_long` → Agent 立刻触发一次紧急压缩（先强制跑一次第 1 层挪走 50K+ 结果，再调摘要）→ 用压缩后的消息列表重试该请求一次；该次重试成功后整体流程继续。F25/F25a/F26
- **AC18（紧急压缩不重复）**：mock provider 在紧急压缩后的重试请求中再次返回 `prompt_too_long` → Agent 不再进入第二次紧急压缩，按错误上抛。F26
- **AC19（PTL 重试 - 摘要自身过长）**：mock provider 对摘要请求返回 `prompt_too_long` → 系统按消息组丢弃策略重试，至多 3 次直接重试（每次丢最旧 1 组）；3 次仍失败则每次再丢 `ceil(剩余×0.2)`（至少 1 组）继续，直至成功或对话耗尽；不会发送 messages 为空的摘要请求。F27
- **AC20（单次行动熔断模型）**：自动阈值触发的压缩行动 3 次重试都没成 → 弹选择菜单（重试 / 分组丢弃重试标明丢量 / 放弃 / 退出 / 其他说明），本轮自动触发停止；手动 `/compact` 行动 3 次重试都没成 → 显示失败原因 + 弹同一菜单，用户可再起新行动；紧急压缩行动 3 次重试都没成 → 报错 + 弹同一菜单，原请求不再重试。子断言：三条路径的失败互不累计——自动行动失败后手动 `/compact` 仍获完整 3 次重试。F28
- **AC20a（自动路径连续失败闸）**：mock provider 持续失败，自动路径连续 3 轮压缩行动都失败 → 第 4 轮达到阈值不再触发自动摘要、不再弹菜单（静默跳过 L2 仅跑 L1）；此时用户手动 `/compact` 成功一次 → 自动路径恢复触发。子断言：手动 / 紧急路径不受闸影响，闸不改变单次行动内部 3 次重试。F28
