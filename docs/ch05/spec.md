# NewCode 结构化 System Prompt 与 Prompt Cache 优化 — 需求规格 (spec.md)

## 背景

ch04 已实现 Agent Loop 与 Plan Mode 两段式，NewCode 能自主多步干活。但系统提示仍是 `resources.py` 的单块字符串 `SYSTEM_PROMPT`，Plan Mode 又通过 `system_suffix` 把 `PLAN_MODE_REMINDER` 硬拼到 system 末尾。由此带来三个问题：

1. **无法按职责扩展**——所有指令堆在一段里，加一条规则就要改整段，改一处影响全局。
2. **缓存完全失效**——Anthropic/OpenAI 对"请求前缀稳定"做自动缓存；Plan Mode 后缀让每次请求的 system 内容都不同，环境信息若进 system 也会每次失效，前缀永不稳定，每轮按全价计费。
3. **关键约定遵守率不稳**——「优先用专用工具」「编辑前必先读」只在一个地方出现一次，模型容易忽略。

范围说明：ch04 加过的 Plan Mode 提示词是**模式/行为指令**；环境上下文（cwd/日期/git/provider+model）从未注入过 system 通道，本章**首次引入**，直接放入 messages 通道首条 user 消息内部，而非"从 system 迁移"。

## 目标

- 全局指令按职责拆成七个固定模块 + 可选模块，按优先级拼装，方便后续插入新模块
- 稳定内容与变化内容分流：稳定的指令与工具描述走可缓存通道，环境信息与补充指令走消息通道（首条 user 消息内分段：段1 稳定系统提示可缓存、段2 环境信息不缓存）
- 工具描述与全局指令双重强化关键规则，提高模型对「优先用专用工具」「编辑前必先读」等约定的遵守率
- 引入带特殊标签的消息（system-reminder）在运行中注入补充指令，不污染缓存、不被模型当作普通用户内容来回复
- Plan Mode 指令不再硬拼进 SystemPrompt，改为按轮次注入 system-reminder（首轮完整、间隔轮次重复、其余精简），控制注入频率
- 从 provider 返回中解析缓存命中信息（写入 / 读取 token），据此验证缓存策略真实生效，并用一组典型场景做人工定性对比
- 跨协议一致：Anthropic 与 OpenAI 两种协议都能正确工作

## 功能需求

### F1: 模块化系统提示拼装

系统提示由七个固定模块按优先级拼装，另有若干可选模块排在固定模块之后。每个模块是独立的指令片段，模块之间用空行分隔。

**七个固定模块及默认优先级（高→低）：**

| 优先级 | 模块 | 职责 |
|--------|------|------|
| 1 | 角色设定（Identity） | 你是谁：AI 编程助手 NewCode，运行在终端，用中文回复 |
| 2 | 行为准则（Behavior） | 怎么跟用户交互：持续工作直到任务完成、无需等待用户确认、可多工具连调 |
| 3 | 工具使用指南（ToolUsage） | 怎么选工具、用工具：优先使用专用工具而非 shell、先读后改、只读可并发 |
| 4 | 代码质量规范（CodeQuality） | 代码该写成什么样：匹配现有代码风格、保持简洁 |
| 5 | 安全边界（Security） | 什么事绝对不能做：只能在工作目录内操作、命令受白名单限制 |
| 6 | 任务执行模式（TaskPattern） | 不同任务怎么处理：复杂任务先探查再动手、按用户请求组织行动 |
| 7 | 输出风格（OutputStyle） | 回复的格式和长度：简洁清晰、Markdown 适度使用 |

> 优先级依据：角色设定 → 行为准则 → 工具使用指南 → 代码质量规范 → 安全边界 → 任务执行模式 → 输出风格。

**可选模块（排在固定模块之后，按需启用）：**

- 自定义指令：读取配置中的自定义 system prompt（`.newcode.yaml` 的 `system_prompt` 字段），空则不生成该模块。**追加语义，不做整体替换**——无论是否配置，七个固定模块始终保留，用户自定义内容只追加在其后（对齐 Claude Code 的 `--append-system-prompt` 语义；这也是安全要求，防止自定义内容绕过内置安全边界与工具使用指令）
- 已激活的 Skill：预留位，本章不实现加载逻辑（见"不做的事"）
- 长期记忆：预留位，本章不实现（见"不做的事"）

**优先级规则：** 每个模块带一个优先级数字，组装时按优先级从高到低排列；同优先级按注册顺序。新增模块只需提供内容与优先级即可插入，无需改其他模块。

### F2: Prompt 组装管线（三通道分发 + 缓存通道规划）

提供一条组装管线，把一次 LLM 请求所需的全部信息分发到三个通道：

| 通道 | 承载内容 | 稳定性 |
|------|---------|--------|
| system（稳定系统提示，物理上为首条 user 消息段1，见 F3） | 七个固定模块 + 可选模块 | 稳定（可缓存，会话内不变） |
| messages | 首条 user 消息段2（环境信息）+ 会话历史 + 按需注入的 system-reminder | 变化（不缓存） |
| tools | 工具定义（含强化后的描述） | 稳定（可缓存，会话内不变） |

管线输出为"协议就绪"的请求结构，均可被 Anthropic 与 OpenAI 适配器直接消费。

**缓存通道规划：**

- 稳定不变的内容（拼装好的稳定系统模块 + 工具定义）归入**可缓存通道**，变化内容（环境信息 + 对话历史）归入**不缓存通道**。
- 可缓存内容必须**跨轮逐字节一致**（不含任何随轮次变化的成分），否则缓存无法命中。
- Anthropic 对稳定内容显式标记缓存断点，使工具定义与稳定系统模块被缓存复用，环境信息块与历史在断点之后不缓存。
- OpenAI 把稳定内容置于请求前缀，靠端点前缀缓存自动受益（不强制端点支持）。

### F3: 环境信息构造与呈现

收集运行环境信息，构造成一段供模型感知环境的文本。环境信息在本章包含：

- 工作目录（cwd）
- 操作系统 / 平台
- 当前日期 / 时间 / 时区
- git 状态（当前分支、是否有未提交修改）
- 应用版本
- 当前 provider 名与模型名

环境信息作为首条 user 消息的**独立第二段**呈现——结构上接在固定模块（段1）之后，物理上与可缓存的稳定模块**分属不同内容块**，自身不进缓存：

```
messages 首条 user 消息（一条消息，内部两段）:
├─ 段1: 固定模块拼装结果（稳定系统提示）  ← 缓存断点（Anthropic）/ 前置稳定前缀（OpenAI）
└─ 段2: 环境信息                         ← 断点之后，不缓存
```

环境信息内容在当前会话内保持稳定（日期跨天会变，但只影响段2，不影响段1 稳定系统提示的缓存）。

### F4: 关键约定双重强化

对模型最易违反的关键约定（如「优先用专用工具而非 shell 拼凑」「编辑文件前必先读取」），在**工具描述**与**系统提示模块**中双重表述，提高遵守率。

### F5: 补充消息注入机制（system-reminder）

提供一种带特殊标签（如 `<system-reminder>`）的补充消息注入形式：构造请求时把补充指令注入**消息通道**，标签语义让模型理解这是系统补充上下文而非用户提问——不针对它直接回复。此类消息**每轮动态构造、不写入持久历史**，因而不污染缓存、不破坏历史角色交替。

### F6: 规划模式按轮次注入

规划模式提醒改由 F5 机制承载（不再拼到系统提示尾部）：

- 按 Agent Loop 轮次控制注入**频率与详略**：**首轮注入完整提醒，之后每隔固定轮次（默认间隔 5 轮）重复一次完整提醒，其余轮次注入精简版**（一行以内）。
- 计数范围：一次规划模式请求的 ReAct 循环内，第 0 轮完整版、第 1–4 轮精简版、第 5 轮再次完整版（若存在）；**仅限当前请求内部，用完即弃，不跨请求累计**。
- 模式跨轮保持，`/plan` 进入、`/do` 退出并触发按计划执行。
- 规划模式下仍仅放开只读工具（沿用 ch04）——只读约束由工具集注册控制，system-reminder 只负责行为提醒，不承担安全隔离。

### F7: 典型场景评估脚本

提供一组（5 个）典型场景的评估脚本，供每次修改 prompt 后做人工对照：

- 场景 1：工具优先级遵守——用户让用 grep/ls 找东西，观察模型是否优先用 search_code/list_files
- 场景 2：先读后改——用户让修改某文件，观察模型是否先 read 再 edit
- 场景 3：Plan Mode 行为——/plan 下只读、产结构化计划，不写文件不执行命令
- 场景 4：多工具配合——一个需多步工具调用的任务，观察调用序列是否合理
- 场景 5：缓存命中与成本——多轮对话中观察 input token 与缓存命中字段变化

每个场景脚本：给定输入、运行一次 Agent、打印完整的工具调用序列与每轮 token 用量、缓存命中字段，供人工对比不同 prompt 配置下的行为差异。脚本不依赖真实 API key 之外的额外服务。

### F8: 缓存命中解析

从 provider 响应用量中解析缓存字段——**缓存写入**（首次创建缓存的 token）与**缓存读取**（命中复用的 token），随用量一并对外暴露，供诊断/调试程序打印验证缓存是否真生效。

- Anthropic 解析其缓存创建/读取字段
- OpenAI 解析其缓存命中字段（端点提供则有，否则为零）

## 非功能需求

### N1: 缓存真实生效与字段解析健壮
缓存命中以 API usage 的实际字段为准（非"设置了标记"），同时要求缓存字段解析健壮：

- **健壮解析**：provider / 兼容端点未返回缓存字段时按零处理，不抛未处理异常、不因缺字段中断本轮或会话。
- **真实生效**（在端点支持缓存计数的前提下）：多轮请求中第二轮起应观测到缓存命中（cache_read / cached_tokens > 0），且每轮 input token 低于未缓存基线。
- **未命中可观测**：若因 prompt 过短未达缓存阈值导致缓存未生效，必须可被观测并上报；若端点本身不返回缓存字段，则本轮无法验证命中，应如实标注"端点不支持缓存计数"，不静默标为通过。

### N2: 双协议行为一致
Anthropic 与 OpenAI（含兼容 base_url）都装配同一套模块化系统提示 + 环境信息、都注入相同补充消息、规划模式注入节奏一致——两协议在**模块内容、注入时机、注入节奏**上行为一致。缓存机制允许按协议不同实现（Anthropic 显式 cache_control，OpenAI 自动缓存），缓存命中解析在各自字段可得时生效。对外可观测行为（工具序列、终止条件、事件流）一致。

### N3: 向后兼容（叠加不改语义）
不破坏 ch04 行为——Agent Loop 多轮编排、流式双路收集、保序分批并发、用户取消、历史一致、用量/迭代进度展示等 ch04 能力**不退化**。系统提示重构与消息注入是**叠加**，不改这些既有路径的语义。`.newcode.yaml` 的 `system_prompt` 字段语义保留（映射为「自定义指令」可选模块）。

### N4: 可观测性
缓存命中/未命中、每轮 input/output token 可在运行中观测（TUI 或评估脚本输出）。改 prompt 前后可通过评估脚本对比行为差异。

### N5: 注入不膨胀
轮次级 system-reminder 不写入会话历史，多轮循环下历史长度不因注入而增长，滑动窗口逻辑不受影响。

### N6: 注入不被误当用户内容
system-reminder 消息以 `<system-reminder>` 标签明确标记，模型不将其当作待回复的用户输入。Anthropic 协议下必须有可靠行为；OpenAI 协议下尽力而为（模型遵循标签语义即可，不做额外保证）。

### N7: 可测试性
缓存验证、注入逻辑、组装管线均可用 mock 驱动真实代码路径测试，不依赖真实 API key 或真实终端。测试环境无 API key 时仍能覆盖绝大部分逻辑。

### N8: 组装开销可控
组装管线（拼接系统模块、环境信息文本、消息序列）每次请求的额外计算开销可忽略（纯字符串拼接与列表构建）；环境信息**采集**阶段（可能外调 shell 获取 git 状态）的成本与降级由 N12 约束。

### N9: 密钥安全（沿用）
API 密钥不回显到对话区或任何输出中（沿用 ch03 N9 / ch04 N9）。

### N10: 缓存标记协议安全
对不支持的协议/模型（如 OpenAI）设置缓存标记不得引发错误或告警——按协议分支跳过即可，任何协议都不因缓存设置而报错。

### N11: 历史合法性
每轮动态注入的补充消息（不持久）拼进请求后，消息序列仍**角色交替合法、工具调用与结果配对不破坏**，不致 provider 返回 400；补充消息不写入持久历史，故不影响后续轮次与可恢复性。

### N12: 环境采集不阻塞、可降级
环境信息采集（含可能外调 shell 的 git 状态）**快速且有界**，不阻塞界面、不显著拖慢请求发起；任一项取不到时降级（留空/省略），不中断会话。

### N13: 代码规范
`ruff format` / `ruff check` 合规（import 分组正确、PEP 8 一致）；可选 `mypy` 通过。

### N14: 可扩展性
新增一类系统提示模块或一类补充消息提醒时，改动局部：不触及装配主逻辑，不改 provider 适配层对外签名的语义稳定性。

## 不做的事

- **NEWCODE.md 项目指令文件加载**：项目级指令文件的扫描、加载与合并。留给章节 7。
- **自动记忆系统**：长期记忆的存取与召回。留给章节 9。本章仅预留「长期记忆」可选模块位。
- **真实 MCP Server 接入**：MCP 协议与外部工具服务对接。留给章节 6。本章仅预留「已激活的 Skill」可选模块位。
- **LLM-as-judge 自动评估管线**：不用模型打分做自动评估，评估仍靠人工跑场景对比。
- **模块内容可配置化**：七个固定模块的内容在本章内固定，不通过配置文件暴露或增删；组装器支持新增模块，但模块清单由代码决定。
- **多语言 system prompt**：不提供多语言版本切换。
- **上下文压缩**：不改变滑动窗口机制，不做历史摘要压缩。
- **缓存命中的 UI 常驻展示**：TUI 不强制新增常驻缓存状态栏；缓存可观测性通过评估脚本输出与现有 token 统计满足。
- **历史增量缓存**：只缓存稳定前缀（工具定义 + 稳定系统模块），不对对话历史另打缓存断点。
- **缓存 TTL / 断点数配置化**：TTL 用默认值（`cache_control: ephemeral`）、断点位置内置，本章不通过配置调整。
- **system_suffix 机制保留**：该机制被 system-reminder 注入替换，本章移除。
- **多模态、流式工具结果**：沿用 ch04，不做。

## 验收标准

- **AC1（模块化组装）**: 组装器将七个固定模块按优先级（角色设定→行为准则→工具使用指南→代码质量规范→安全边界→任务执行模式→输出风格）拼装成完整系统提示，模块间空行分隔；插入一个测试模块（如"自定义指令"）后，其内容出现在固定模块之后。
- **AC2（三通道分发）**: 组装管线正确分发：首条 user 消息段1 含七个模块（稳定），段2 为环境信息，tools 通道含六个工具定义。环境信息变更（如日期变化）不改变段1 稳定内容。
- **AC3（环境信息内容）**: 环境信息段包含工作目录、操作系统/平台、当前日期/时间/时区、git 状态（分支、未提交修改）、应用版本、激活的 provider 名与模型名，且全部可被模型读取。
- **AC4（关键约定双重强化）**: 六个工具（read_file/edit_file/write_file/execute_command/list_files/search_code）的 description 均含用法与配合关系；「优先用专用工具」「编辑前必先读」两条规则在工具描述与全局指令中均出现。
- **AC5（Anthropic 缓存标记）**: Anthropic 协议下，首条 user 消息段1（稳定模块）与 tools 通道的请求结构中包含 ephemeral 缓存标记；组装后的稳定前缀 + 工具定义总长须 ≥ 缓存生效阈值（约 1024 token，否则缓存无法命中，组装器对稳定前缀长度做校验并在不达标时日志告警）；在端点返回缓存计数的前提下，多轮请求中第二轮起 usage 出现 cache_read_input_tokens > 0，且每轮 input token 明显低于首轮基线（基线 = 首轮缓存未命中/创建时的 input token 数）。
- **AC6（OpenAI 无缓存标记）**: OpenAI 协议下，请求结构中不包含任何缓存标记字段，请求正常发出不报错；usage 中 cached_tokens 字段被正确解析。
- **AC7（缓存失效可观测）**: 验证过程中，`cache_read / cached_tokens == 0` 能区分两种原因：① prompt 过短未达缓存阈值导致缓存未命中——可观测并如实上报"未命中"；② 端点不返回缓存字段（兼容端点）——如实标注"端点不支持缓存计数"，标注为待人工验证。两种情况均不静默标为通过。
- **AC8（system-reminder 注入）**: system-reminder 以 role=user、`<system-reminder>` 标签包裹的形式注入；每轮动态构造、不写入持久历史；模型不将其作为普通用户内容回复（Anthropic 协议下验证；OpenAI 协议下尽力而为，见 N6）。
- **AC9（规划模式按轮注入）**: 稳定系统提示中不再出现规划模式指令文本；一次规划模式请求内第 0 轮注入完整版、第 1–4 轮注入精简版、第 5 轮再次注入完整版（若存在）；只读约束仍生效。
